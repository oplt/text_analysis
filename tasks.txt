AUDIT SCOPE AND CONFIDENCE

This audit followed the implemented call chains for RAG ingestion, parsing, chunking,
embedding, vector/lexical retrieval, query planning/expansion, fusion, parent expansion,
reranking, context construction, structured answer generation, citation validation,
Ask Corpus, corpus synthesis, caching, provenance, database models/migrations, evaluation
fixtures, and research-facing UI paths.

Confirmed findings below are based on source behavior at the audited commit. Items marked
NEEDS BENCHMARK or NEEDS REPRODUCTION are intentionally not presented as confirmed defects.

The repository could not be cloned into the execution sandbox because outbound DNS access
to github.com is unavailable. GitHub source inspection was performed through the repository
connector. No repository test suite was executed in this audit session. A query for
pull-request-triggered workflow runs at the audited commit returned no runs, so CI success
must not be inferred.

CRITICAL FINDINGS

1. CONFIRMED P0: CorpusScopeSnapshot stores independently sorted rag_document_ids and
   corpus_document_ids, while corpus synthesis reconstructs a mapping with zip(...,
   strict=False). The lists do not have a guaranteed 1:1 relationship, and the corpus list
   includes unavailable/unindexed documents. This can assign citations to the wrong
   corpus_document_id.
2. CONFIRMED P0: Fixed research-assistant scopes persist an evidence_revision_hash, but
   retrieval selects RagDocument.current_revision_id and accepts the caller-supplied historical
   evidence hash without proving that returned chunks belong to that frozen evidence revision.
   Reindexing a document can therefore return new evidence while labeling it with an old hash.
3. CONFIRMED P0: Queued corpus synthesis persists scope/evidence metadata, but the worker
   later calls synthesize() and resolves the live corpus again. A queued run can execute
   against a different corpus/index state than the state that was queued.
4. CONFIRMED P1: Retrieval cache hits replace the real fusion provenance with
   fusion_method="cached"; the cache payload contains chunks only, and the cache key does not
   directly encode the evidence revision or every algorithm parameter.
5. CONFIRMED P1: Hybrid dense and lexical branches are awaited sequentially for each query
   variant. Contradiction multi-query performs repeated sequential branch work, adding avoidable
   latency.
6. CONFIRMED P1: JSON embedding fallback preselects a bounded set ordered by updated_at and
   only then computes similarity in Python. Once the candidate cap is hit, relevant older
   chunks can be omitted with no explicit degraded answer contract.
7. CONFIRMED P1: PostgreSQL FTS is hard-coded to the 'simple' configuration. This provides
   a safe language-neutral fallback but does not exploit English/German/French/Turkish
   stemming or language metadata.
8. CONFIRMED P1: PDF parsing has a useful PyMuPDF block path, but no text-quality gate, OCR
   path, table extraction, header/footer suppression, or explicit multi-column reconstruction.
   "reading_order=pymupdf_blocks" is not sufficient evidence of robust academic reading order.
9. CONFIRMED P1: char_start/char_end are offsets within each ParsedDocument, but API citation
   objects do not carry an explicit offset_scope. A PDF ParsedDocument is page-scoped while
   Markdown/DOCX ParsedDocuments can be section-scoped. The same coordinate fields are therefore
   ambiguous to downstream highlighting.
10. CONFIRMED P1: Parent windows group every N leaf chunks without respecting page/section
    boundaries. Their first char_start and final char_end can describe different local coordinate
    spaces when the group crosses ParsedDocument boundaries.
11. CONFIRMED P1: The offline retrieval benchmark is valuable but consumes pre-ranked
    dense/lexical fixture lists. It does not execute parsing, chunking, embeddings, pgvector/FTS
    SQL, filters, ANN behavior, cache behavior, or real end-to-end retrieval.
12. CONFIRMED P1: Corpus synthesis maps all considered document findings into one reduction
    prompt. The configured synthesis_max_documents is not used by the shown synchronous map/
    reduce path; large corpora can overflow prompt/context limits despite batched map retrieval.

TASK RAG-P0-001 — Replace parallel corpus/RAG ID lists with explicit relational mappings

Priority: P0
Category: CORRECTNESS, CITATION, REPRODUCIBILITY
Status: TODO

Problem:
Corpus-to-RAG identity is represented partly as parallel arrays. Those arrays are not
guaranteed to have identical membership or ordering, yet corpus synthesis rebuilds a map by
zipping them. This can attach a valid chunk citation to the wrong CorpusDocument.

Evidence:
CorpusScopeService._build_snapshot() builds rag_document_ids as sorted(indexed) but
corpus_document_ids as sorted(all corpus document ids), including unavailable documents.
CorpusSynthesisService later executes zip(scope.rag_document_ids,
scope.corpus_document_ids, strict=False) to build rag_to_corpus_document.

Why it matters:
Wrong document identity is evidence corruption: citation links can point at the wrong
research object even when the chunk itself is valid. This invalidates research provenance and
can mislead memo/synthesis persistence.

Current flow:
CorpusDocument rows -> two independent lists -> synthesis zip -> corpus_document_id on citation.

Target flow:
CorpusDocument rows -> explicit immutable mappings [{corpus_document_id, rag_document_id,
availability, revision_id}] -> retrieval/synthesis/citation use the mapping by key.

Best solution:
Introduce a CorpusEvidenceMember/ScopeDocument value object containing both IDs and
availability metadata. Make CorpusScopeSnapshot serialize a documents array (or mapping) and
derive compatibility lists from it. Remove all semantic use of zip between independently built
ID collections. Use _rag_to_corpus_document_map() style keyed lookups consistently. Fail closed
if a returned citation document is not present in the frozen mapping.

Alternative solutions:
None.

TASK RAG-P0-002 — Make fixed assistant scopes revision-addressed instead of hash-labeled live retrieval

Priority: P0
Category: REPRODUCIBILITY, CORRECTNESS, RETRIEVAL
Status: TODO

Problem:
A fixed Ask Corpus thread persists an evidence_revision_hash, but that hash is not used to
select exact chunk revisions. Retrieval queries always join against each RagDocument's
current_revision_id. The retrieval service then accepts a caller-provided evidence hash without
verifying that selected chunks match it.

Evidence:
CorpusScopeService.resolve_for_thread() returns the persisted fixed scope.
CorpusAssistantService passes scope.rag_document_ids and scope.evidence_revision_hash into
RetrievalService. RagRepository._retrieval_scope_filters() enforces
d.current_revision_id = c.revision_id. RetrievalService sets outcome.evidence_revision_hash to
the supplied hash when present.

Why it matters:
After reindexing, a historical/fixed research conversation can use new evidence while
displaying the old evidence revision. That is a direct reproducibility and provenance failure.

Current flow:
fixed scope {document IDs, old hash} -> live current_revision chunks -> outcome labeled old hash.

Target flow:
fixed scope {document ID -> exact revision ID} -> revision-filtered retrieval -> recompute/
verify evidence hash -> only then generate and persist answer.

Best solution:
Extend the frozen scope to capture exact RagDocumentRevision IDs per document. Add a
RevisionSelection object to retrieval. Repository SQL must support either current revision
(default/live mode) or an explicit revision allow-list. Retrieval must compute the evidence hash
from the actual selected chunk revisions and compare it to the requested frozen hash; mismatch
must fail with stale_evidence_revision, not relabel the result.

Alternative solutions:
None.

TASK RAG-P0-003 — Execute queued corpus synthesis from the frozen queued snapshot

Priority: P0
Category: SYNTHESIS, REPRODUCIBILITY, CORRECTNESS
Status: TODO

Problem:
Queued synthesis stores scope_hash, evidence_revision_hash and documents_in_scope, but the
worker ignores that frozen scope and calls synthesize(), which resolves the current corpus again.

Evidence:
CorpusSynthesisService._enqueue() persists scope/evidence fields in run.parameters_json.
execute_synthesis() reads query and document_subset, then calls self.synthesize(...,
async_mode=False). synthesize() invokes CorpusScopeService.resolve() again.

Why it matters:
Queue delay, reindexing, deletion, corpus edits or availability changes can change the
evidence used by a historical synthesis run. The final run can overwrite its stored evidence hash
with the new live result.

Current flow:
enqueue frozen metadata -> worker -> re-resolve live corpus -> map/reduce current evidence.

Target flow:
enqueue immutable synthesis snapshot -> worker loads exactly that snapshot -> map exact
document revisions -> hierarchical reduce -> persist same snapshot identity.

Best solution:
Persist a SynthesisScopeSnapshot with explicit corpus membership, RAG IDs, exact revision IDs,
index/retrieval versions and evidence hash. execute_synthesis() must deserialize and validate that
snapshot instead of calling normal live scope resolution. If an exact historical chunk revision
is unavailable, fail the run with historical_revision_unavailable and preserve queued provenance.

Alternative solutions:
None.

TASK RAG-P1-011 — Persist complete embedding identity in immutable index revisions and cache keys

Priority: P1
Category: EMBEDDING, REPRODUCIBILITY
Status: TODO

Problem:
RagDocumentRevision records source/parser/chunker/index version but not embedding provider/model/
model version/dimensions or preprocessing identity. Chunk metadata contains some embedding fields,
and EmbeddingService calls embed_texts_with_cache without passing configured dimensions.

A reproducible index must prove how vectors were created. Same provider/model names can have

Add embedding fields to RagDocumentRevision and evidence revision identity. Pass dimensions to
embed_texts_with_cache. If provider exposes immutable model revision/deployment ID, persist it;
otherwise store configured model string plus provider SDK/API version where practical. Validate
all returned vectors before storage.

TASK RAG-P1-008 — Add PDF text-quality assessment, selective OCR, reading-order validation and table provenance

Priority: P1
Category: PARSING, CITATION
Status: TODO

Problem:
PDF support has a good native-text baseline, but pages with poor extraction are not scored and
selectively OCR'd. Multi-column order, tables, repeated headers/footers, captions and scanned pages
remain weak.

Evidence:
EnhancedPdfParser uses PyMuPDF get_text('dict') blocks in emitted order, soft-dehyphenates
'-\n', and records no table extraction or OCR. BasicPypdfParser also reports ocr_ran=False.
parse_pdf_with_fallback falls back parser-wide, not page-quality-driven.

Why it matters:
Academic PDFs often contain exactly these structures. Parsing errors propagate into chunking,
retrieval, source offsets and citations; no retrieval algorithm can recover text that was lost or
misordered.

Current flow:
native parser -> blocks/text -> chunks.

Target flow:
native extraction per page -> quality assessment -> OCR only on low-quality/scanned pages ->
layout ordering -> table/caption extraction -> stable source blocks -> chunking.

Best solution:
Introduce a page-level ParsedPage/SourceBlock representation. Compute quality signals:
printable-character ratio, glyph/text density, replacement-char ratio, suspicious line order and
empty-page status. OCR only flagged pages. Preserve native and OCR provenance, bounding boxes,
block type, table/caption IDs and parser versions. Evaluate multi-column academic fixtures.

None.

Category: PERFORMANCE, DATABASE, OBSERVABILITY
Status: TODO

Problem:
The code includes batching and ANN health checks, but expected limits for ingestion, retrieval,
scope materialization, synthesis and frontend evidence rendering are not documented with measured
load behavior.

Evidence:
CorpusScopeService pages all corpus documents into memory to create a complete deterministic
scope; synthesis iterates every document; retrieval uses bounded candidates. No inspected artifact
documents empirical 100/1k/10k/100k document or 10k/100k/1M chunk limits.

Why it matters:
Research users need predictable operating envelopes; premature distributed infrastructure is
not justified without measurements.

Current flow:
component-level implementation with implicit scale assumptions.

Target flow:
documented scale matrix + load benchmarks + thresholds that trigger background jobs/ANN/
hierarchical synthesis.

Best solution:
Create reproducible load generators using synthetic metadata/text and measure DB size, indexing
throughput, embedding throughput, retrieval P50/P95/P99, scope resolution, synthesis scheduling and
memory. Profile 10k, 100k and 1M chunks; extrapolate higher only when justified.

Alternative solutions:
None.

TASK RAG-P3-026 — Evaluate optional claim-entailment validation only after structural citation guarantees

Priority: P3
Category: CITATION, EVALUATION
Status: TODO

Problem:
Structural citation validity proves that a claim cites retrieved authorized evidence, not that
the cited text semantically entails the claim. An entailment layer may help, but making an LLM
judge mandatory now would add cost/latency and another failure mode.

Evidence:
Current CitationValidationService is intentionally structural/string-level; no entailment model
is required.

Why it matters:
Optional semantic support scoring could reduce subtle unsupported claims after the P0/P1
provenance work is correct.

Current flow:
structural validation only.

Target flow:
structural validation mandatory; optional benchmarked entailment/NLI support score as a second
layer with transparent uncertainty.

Best solution:
Build an offline experiment using a labeled claim-evidence set. Compare a lightweight NLI
cross-encoder and, separately, provider-based judging. Measure false positive/negative rates,
latency and multilingual behavior. Adopt only if it materially improves unsupported-claim
detection without blocking valid citations.

Alternative solutions:
None.

Files involved:
- backend/modules/rag/application/citation_validation_service.py
- backend/modules/rag/eval/retrieval_eval.py

Files to add:
- backend/modules/rag/eval/citation_entailment_experiment.py

Database changes:
None.

API changes:
None.

Frontend changes:
None.

Configuration changes:
Optional CitationEntailmentConfig, disabled by default.

Algorithm:
for (claim, cited evidence): support_score = NLI(claim, evidence)
aggregate conservatively; threshold selected on labeled validation set, not intuition

Performance considerations:
Potentially expensive; batch and keep optional. Never delay normal RAG until benchmark
justifies production use.

Backward compatibility:
Disabled by default.

No data migration required.

Tests required:

- latency/cost report

TECHNICAL DEBT / FUTURE RESEARCH
================================

These items MUST NOT block the production-quality architecture above and should only be pursued
against the end-to-end benchmark:

1. Weighted RRF. Current pure RRF is explicit and robust. Evaluate branch weighting per query
   profile only after qrels are large enough to avoid overfitting.
2. Learned fusion. Do not introduce until there is sufficient labeled retrieval data and a stable
   feature/provenance contract.
3. ColBERT / late interaction. Consider only if dense+FTS+rerank cannot meet recall on long or
   fine-grained academic passages within latency/cost targets.
4. GraphRAG / knowledge graphs. Consider only for demonstrated multi-hop/entity-relation research
   questions; do not replace canonical text provenance.
5. Contextual chunk embeddings. Evaluate against current structure-v1 baseline; retain exact source
   spans and embedding identity.
6. Adaptive retrieval / routing models. Prefer explicit rules first; learned routing requires
   benchmark evidence and inspectable fallback.
7. Self-RAG / CRAG. Treat as experimental orchestration, not a substitute for revision/ACL/citation
   correctness.
8. Semantic caching. Only after retrieval cache provenance is correct; never cache across evidence
   revisions or authorization scopes.
9. Citation entailment model. Tracked as RAG-P3-026; optional after structural guarantees.
10. Provider-based LLM reranking. Keep optional due latency, cost and reproducibility concerns.

DEPENDENCY REVIEW
=================

Retain / preferred:
- PyMuPDF: useful native PDF layout/block extraction; keep pypdf fallback.
- pypdf: reliable baseline/fallback, not sufficient for layout/scanned PDFs alone.
- pgvector: appropriate because PostgreSQL already owns ACL/revision/filter data; avoids a second
  vector authorization plane.
- PostgreSQL FTS: appropriate baseline hybrid lexical store; benchmark before adding a new search
  service.
- langchain-text-splitters: acceptable as a bounded oversized-unit splitter, but canonical
  structure/provenance logic should remain owned by this repository.
- provider embedding APIs / existing embedding adapter: retain behind explicit EmbeddingIdentity.
- sentence-transformers CrossEncoder: optional reranker only after benchmark; maintenance includes
  model download/runtime footprint and multilingual model choice.

Optional additions only when justified:
- OCR engine: optional dependency behind selective PDF quality gate; cost is CPU/runtime/packaging.
- Table extractor: optional because PDF tables are heterogeneous and dependency footprint can be
  large.
- language detection library: only if deterministic heuristic/metadata is insufficient in
  multilingual benchmark.
- NLI/citation entailment model: optional experimental layer, not required for correctness.

Avoid adding:
- a separate vector database while PostgreSQL/pgvector meets measured requirements;
- a separate Elasticsearch/OpenSearch cluster solely for BM25 before PostgreSQL FTS is benchmarked;
- general agent frameworks for deterministic query planning/fusion;
- GraphRAG/knowledge graph infrastructure without an observed multi-hop failure class.
