# 1. NON-NEGOTIABLE ARCHITECTURAL RULE

Preserve this distinction:

```text
RAG chunks != research TextUnits
```

RAG chunks exist for retrieval.

Research `TextUnit`s and canonical research sources exist for:

* reproducible frequency analysis
* KWIC
* DFM
* keyness
* dictionary analysis
* statistical analysis
* annotation
* reliability
* classifiers
* topic models
* other deterministic research calculations

Never reconstruct research-analysis text by joining overlapping RAG chunks.

Never replace deterministic research calculations with LLM answers.

The desired dependency direction is:

```text
text_research
    |
    +----> rag
```

Do NOT make the generic RAG bounded context depend directly on `text_research`.

Corpus-aware assistant endpoints/services should live in or be orchestrated from `text_research`, delegating generic retrieval/generation to the RAG module.

# 2. PRODUCT CONCEPT

The researcher-facing feature should be called:

```text
Ask Corpus
```

or internally:

```text
Research Assistant
```

Do not expose the term "RAG" as the primary researcher-facing concept.

RAG becomes the evidence/provenance layer for questions such as:

* What do these documents say about X?
* Which documents support this interpretation?
* Find counter-evidence for this claim.
* Compare how groups/documents discuss X.
* Find passages conceptually related to X even without exact terminology.
* Explain this topic-model result using representative passages.
* Find passages that help interpret a keyness result.
* Find semantically related dictionary candidates from the corpus.
* Compare positions across source documents.
* Produce corpus-grounded research memos.
* Perform broader corpus synthesis with explicit source coverage.

The system must never imply that generated interpretation is equivalent to deterministic statistical evidence.

# 8. CLAIM-LEVEL CITATIONS

The current approach where every retrieved chunk becomes a citation is insufficient for research software.

Upgrade generation to use structured citation output.

The LLM should return structured data conceptually similar to:

```json
{
  "answer": "Synthesized answer text...",
  "claims": [
    {
      "text": "Policy increasingly emphasized activation.",
      "chunk_ids": ["chunk-id-1", "chunk-id-9"]
    },
    {
      "text": "Collective provision remained important in several documents.",
      "chunk_ids": ["chunk-id-15"]
    }
  ]
}
```

Use the project's existing structured-output mechanisms if available.

Server-side validation MUST ensure:

* every cited chunk exists
* every cited chunk was actually retrieved for this answer
* every cited chunk belongs to an allowed document
* every allowed document belongs to the resolved corpus/scope
* malformed citations are discarded or treated as generation validation failure
* the frontend never trusts arbitrary model-generated document IDs

Generate a stable citation presentation such as:

```text
[1]
[2]
[3]
```

Map these identifiers to validated source objects.

An answer should cite only evidence actually used to support claims.

Do not automatically present every retrieved chunk as "cited."

# 12. REAL HYBRID RETRIEVAL

The existing implementation performs vector retrieval first and only then lexical/vector reranking.

Upgrade this to true independent hybrid retrieval.

Desired architecture:

```text
                        query
                          |
             +------------+------------+
             |                         |
             v                         v
       dense retrieval           lexical retrieval
         pgvector            PostgreSQL FTS/BM25-like
             |                         |
             +------------+------------+
                          |
                          v
                     rank fusion
                          |
                          v
                  optional reranker
                          |
                          v
                 source diversification
                          |
                          v
                       top K
```

Implement an independent lexical retrieval path.

Prefer PostgreSQL-native full-text search unless the current stack provides a better clean abstraction.

Use a robust fusion strategy such as:

* Reciprocal Rank Fusion (preferred baseline), or
* another properly justified rank fusion algorithm

Do not merely combine raw scores from incomparable scales without normalization.

Refactor responsibilities cleanly, potentially with interfaces such as:

```text
DenseRetriever
LexicalRetriever
HybridRetriever
RetrievalFusion
Reranker
```

Keep the system testable.
