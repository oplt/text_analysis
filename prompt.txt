# PHASE 2 — BLIND RELIABILITY CODING ✅

Add an explicit annotation mode separating:

```text
BLIND HUMAN RELIABILITY
```

from:


## Blind mode rules ✅

When a campaign is blind:

Annotators MUST NOT see:

* other annotators' decisions,
* adjudicated values,
* model predictions,
* LLM suggestions,
* reliability results before completing their own assigned coding,
* consensus labels.

This is required to avoid anchoring and coder contamination.

Inspect:

```text

```

Current `AnnotationView.tsx` retrieves classifier predictions for annotation units.

Change this so prediction retrieval is conditional on the campaign mode.

Conceptually:

```tsx
if (campaign.blind_mode) {
    do not fetch predictions;
}
```

Do not merely hide an already-fetched model result in CSS.

## UI ✅

In campaign setup make the distinction explicit:

```text
Annotation mode

○ Blind reliability coding
  Independent human coding.
  Model predictions and other coders' decisions are hidden.

○ AI-assisted coding
  Model/AI suggestions may be shown to annotators.
```

Persist the selected mode in campaign provenance.

# SUCCESS CRITERIA

The work is successful when:

```text
CI is green.

Two or more researchers can participate in a formally defined annotation campaign.

Blind reliability coding cannot expose machine predictions or other annotators' decisions.

Cohen's kappa works correctly for two coders.

Fleiss' kappa is available and visible for appropriate 3+ coder designs.

Krippendorff's alpha supports incomplete multi-coder designs.

Reliability results include reproducible confidence intervals.

Reliability is campaign/unit-type/codebook-version scoped.

Supervised feature selection exists and is leakage-safe.

Research stage cache artifacts can be reused across worker processes/containers.

Duplicate expensive computations are protected by distributed locks.

SSE run updates use Redis events instead of querying PostgreSQL every second per connected client.

PostgreSQL remains the durable run-state source.

Model lifecycle is manageable from the frontend.

Prediction sets are inspectable from the frontend.

Drift monitoring is available from the frontend.

Existing StatisticalModelView and MeasurementComparisonView are actually routed.

Runs contain enough provenance to reproduce and audit scientific analyses.

Large-corpus operations use batching/streaming/bulk operations where appropriate.

Celery/sklearn/BLAS parallelism remains bounded and does not create nested CPU oversubscription.
```

The priority is not to add the largest number of algorithms.

The priority is to make `text_analysis` a trustworthy computational social-science platform whose outputs can be defended in a publication, reproduced later, scaled to substantially larger corpora, and audited from raw corpus through annotation, preprocessing, feature construction, modeling, evaluation and final result.

I would use this as the **top-level Cursor implementation prompt**, then implement it phase by phase rather than asking Cursor to modify the entire repository in one pass.
