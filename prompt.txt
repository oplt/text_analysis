# 2. Backend ↔ frontend capability audit

Perform a systematic comparison between backend capabilities and frontend functionality.

For every significant backend endpoint/service/capability, determine:

1. What does the backend already support?
2. Is it exposed through the frontend?
3. Is the UI implementation complete?
4. Is the functionality partially exposed?
5. Is there an API that appears unused?
6. Is the frontend recreating logic that already exists in the backend?
7. Are API response fields being ignored even though they could improve the UI?

Create a capability matrix such as:

| Backend capability | API/service    | Frontend support | Status   | Recommended action |
| ------------------ | -------------- | ---------------- | -------- | ------------------ |
| X                  | `/api/...`     | Dashboard        | Complete | None               |
| Y                  | `/api/...`     | None             | Missing  | Build UI           |
| Z                  | service/module | Settings         | Partial  | Complete UI        |

Prioritize useful existing backend capabilities that are missing or incomplete in the frontend.

Then **implement those capabilities in the UI**.

Do not invent arbitrary features simply to increase feature count. Prefer functionality already supported by the architecture.

# 4. Performance audit and optimization

Measure before optimizing whenever practical.

Inspect both backend and frontend performance.

## Backend

Investigate whether any of the following would materially improve performance:

* `asyncio`
* concurrent I/O
* connection pooling
* database pooling
* HTTP client pooling
* Redis or application caching
* memoization
* batch operations
* bulk database operations
* pagination
* lazy loading
* background tasks
* queues/workers
* prefetching
* query optimization
* proper DB indexes
* reduced serialization overhead
* response compression
* avoiding redundant computation

### Critical rule

Do **not** introduce asyncio, caching, pools, Redis, workers, or architectural complexity simply because they sound faster.

First identify the bottleneck.

Then choose the simplest appropriate optimization.

For example:

* I/O-bound independent operations → consider concurrency/asyncio
* repeated expensive reads → consider caching
* high DB connection churn → use pooling
* N+1 queries → fix the query rather than adding caching
* repeated HTTP calls → reuse an HTTP client/session and connection pool
* CPU-bound work → do not pretend asyncio solves it
* slow background work → consider worker/task execution

Check for blocking libraries used from asynchronous request handlers.

Prefer reusable long-lived clients/pools over constructing clients for each request.

Ensure optimizations preserve correctness.

* use sensible axes
* provide units
* format values appropriately
* provide tooltips
* handle empty data
* handle loading
* handle errors
* remain responsive

# 17. Prioritization

Use this order:

### P0 — correctness/security

* crashes
* data corruption
* authentication/authorization bugs
* severe security issues

### P1 — broken/incomplete functionality

* backend capabilities missing from UI
* partially implemented user journeys
* broken flows

### P2 — performance

* obvious bottlenecks
* N+1 queries
* blocking async operations
* unnecessary sequential I/O
* duplicated requests
* expensive frontend rendering

### P3 — UX

* poor page hierarchy
* inconsistent loading/error/empty states
* unbalanced pages
* confusing interactions

### P4 — visualization and polish

* improved analytics
* MUI charts
* dashboard refinements
* minor modernization

Do not spend significant time polishing minor UI details while P0–P2 issues remain.

# Important constraints

* Do not make cosmetic changes merely to create activity.
* Do not rewrite the application unnecessarily.
* Do not introduce infrastructure without a demonstrated need.
* Do not introduce breaking API changes unless unavoidable.
* Do not remove functionality.
* Do not weaken validation, typing, security, or tests.
* Do not blindly cache mutable data.
* Do not blindly parallelize operations with dependencies.
* Do not use asyncio for CPU-bound work and claim it improves CPU performance.
* Do not add commercial MUI components requiring a license unless the project already uses/permits them.
* Do not replace a useful table with a chart when precise values are more important.
* Do not add decorative visualizations.
* Follow the repository's established conventions unless they are themselves the source of a problem.

The final objective is:

> Make the existing application more complete, correct, fast, coherent, and useful by fully leveraging capabilities that already exist in the repository, while improving the architecture only where evidence justifies doing so.
